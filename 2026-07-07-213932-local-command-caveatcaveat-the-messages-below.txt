⏺ Design — Section 2 of 2: Audit architecture

  Lens structure. Four parallel exploration lenses, each an Opus 4.8 xhigh
  agent, each primed with the exact baseline numbers, the 2026-07-03 catalog,
  and its execution corrections — so nobody re-reports executed or
  definitionally-retired items:

  1. Normalization & boilerplate — fresh-eyes repetition/residue sweep of the
  post-W9 tree (the W0–W9 waves themselves left seams: new primitives with
  near-miss consumers, half-migrated patterns).
  2. Abstraction, DI & decorator deepening — residual hand-wired seams the
  inversify/@OnEvent/tRPC spine hasn't absorbed yet: remaining manual lifecycle
  rituals, AOP candidates (@NotifiesFailure-class patterns), declarative-table
  conversions.
  3. Architecture-breaking — structural moves the finished spine newly enables
  (the prior cycle's biggest finds — A8, A9 — were of this class).
  4. Framework adoption — the four reopened options plus a scan for new
  candidates (any hand-rolled subsystem with a battle-tested replacement). Every
  claim ships with its verification command embedded.

  Spike protocol. Spikes run in isolated git worktrees (one executor per tree —
  standing rule), are throwaway, and nothing merges. Each has a pre-declared
  pass/fail criterion:
  - comlink: golden byte-test parity on the frame path + perf within a declared
  budget; transferable handling confirmed.
  - own-transport: minimal typed IPC link over ipcMain/MessagePorts that
  provably fixes the falsy-input drop; LOC of the owned transport vs. the
  electron-trpc surface it deletes.
  - Lit: render one real component preserving all id= attrs; e2e
  selector-survival check.
  - NestJS: service recount against the ~20 threshold first; bootstrap probe
  only if it crosses.

  Verification. Same discipline as last cycle: I re-run every load-bearing count
  deterministically myself (scripts in session scratchpad), log corrections in
  the catalog header, and personally review all lens output — review is never
  delegated. Lens-overlap gets deduplicated in the totals; anything I can't
  independently reproduce is marked as agent-confidence, explicitly.

  Deliverables & sequence. (1) This design doc →
  docs/superpowers/specs/2026-07-05-<topic>-design.md; (2) the audit runs; (3)
  2026-07-05 opportunity catalog lands beside it — ranked table, framework
  verdicts with spike evidence, verification appendix; (4) you review the
  catalog at explicit decision points (accept/reject each framework verdict,
  approve ranking); (5) accepted items become wave execution plans via
  writing-plans, same cadence as W0–W9.

  Look right? If so, I'll write the design doc and run the spec self-review.

❯ fully leveraging its bolierplate reduction                                    

⏺ Good challenge — and yes, the REJECT holds even for maximal adoption, because
  the boilerplate Nest is famous for deleting is either already deleted here, or
  unavailable for the same reasons it's unavailable to inversify. Itemized
  against Nest's actual reduction levers:

  1. Autowired constructor injection — unavailable, definitionally. Nest's
  headline win (no explicit tokens) rides on design:paramtypes metadata, exactly
  like inversify's autowiring. Your codebase injects interface-typed structural
  ports (-Like types, the inversify-free @platform rule), and TypeScript erases
  those to Object — the A11 standing retirement. Nest hits the identical wall:
  every one of those injections needs an explicit @Inject(TOKEN), which is
  precisely what you write today. Nest's wiring floor equals your current floor.
  2. Lifecycle hooks (OnModuleInit/OnModuleDestroy) — already built, and Nest's 
  version can't replace it. Your BaseService/BaseOrchestrator lifecycle template
  is the in-house equivalent, and it must keep existing regardless, because
  Nest doesn't run in the renderer — where most of your services live. Adopting
  Nest hooks for main's 12 services deletes nothing (the bases stay for the
  other ~30+ classes) and forks the framework model across processes, the exact
  grounds "no-container-in-main" was rejected last cycle. The real
  lifecycle-boilerplate win in the tree is the base-class rework bundle
  (−80…−160), which fixes it for both processes.
  3. @nestjs/event-emitter-style @OnEvent — you already shipped it. The typed
  @OnEvent + auto-bind spine landed in W4a. The residue (BaseService's manual
  bindEventHandlers at 5 sites) is a 10-line fix in the existing base, already
  in the catalog.
  4. Module system / request pipeline (guards, interceptors, pipes, middleware) 
  — no surface to bite. That machinery deletes boilerplate in apps with routing
  and request-scoped cross-cutting concerns. Main has no routes; its IPC
  pipeline is 14 tRPC procedures already folded through rethrowAsTrpcError and
  zod schemas. The thing Nest's pipeline would replace is ~60 LOC of module
  bindings — replaced with more ceremony (@Module graphs, a Nest bootstrap,
  provider arrays).
  5. Nest as the IPC transport (custom microservice strategy) — that's 
  own-transport wearing a uniform. Building an Electron-IPC transport strategy
  for Nest re-implements everything the own-transport verdict just rejected on
  arithmetic, and additionally loses tRPC's end-to-end renderer type inference
  (Nest controllers don't project typed clients without codegen bolt-ons).

  The honest framing: NestJS's boilerplate reduction is real in the environment
  it targets — many-module server apps with HTTP/microservice surfaces and
  class-typed injection. This app is a two-process Electron system whose main
  side is 12 services and one 60-LOC binding module, whose injection style is
  structurally incompatible with autowiring (by deliberate architecture, not
  accident), and whose event/lifecycle/error decorators were already
  purpose-built in W1–W6. Full leverage was the evaluation — there's simply
  nothing left on the table for it to lift.

  inventory explicitly (lever-by-lever, not just the service count) so the
  rejection is durable against this exact question next cycle. Spikes are still
  running in the background — I'll pick up catalog assembly when they land.

❯ what other language could we use ?                                            

⏺ Short answer: for this app, none of the credible alternatives pass the
  reduction test — and the reason is structural, not taste. The app's core
  capability is Chromium's media stack: the GameBoy capture device comes in
  through getUserMedia/MediaStream, recording through MediaRecorder, rendering
  through WebGPU-in-Chromium. Any language that takes you off Electron takes you
  off Chromium, and that's the one dependency you can't rewrite. Candidate by
  candidate:

  - Rust (Tauri v2) — the only alternative worth taking seriously. It replaces
  the main process with Rust and keeps a TS renderer over the system webview.
  Two problems. First, it attacks the smallest part of your codebase: main is 12
  services and a 60-LOC module; the renderer + platform TS (the overwhelming
  bulk) stays TS regardless. Second, it swaps Chromium for WKWebView/WebView2,
  where UVC getUserMedia behavior, codec availability, and WebGPU maturity are
  inconsistent across platforms — it puts the capture path itself at risk to
  rewrite the part that's already small. It's a rewrite wearing a reduction
  costume: LOC doesn't shrink, it relocates into a second toolchain plus an FFI
  seam.
  - Go (Wails) — same webview story as Tauri with a weaker desktop ecosystem for
  this domain. Same verdict, less upside.
  - Native Swift/AVFoundation (or C++/Qt) — genuinely excellent capture stacks,
  but it's a different product: platform-locked (you ship cross-platform,
  including AppImage) or a multi-year Qt rewrite that would balloon LOC, and
  you'd forfeit a working 2,030-unit/91-e2e verification estate to re-earn it
  from zero.
  - Compile-to-JS alternatives (ReScript, Elm, etc.) — lateral. Same platform,
  different syntax, total churn, and you'd orphan the exact libraries doing your
  heavy lifting (zod, tRPC, inversify, signals).
  - WASM (Rust/Zig) for hot paths — the frame path is GPU-bound, not CPU-bound,
  and the GPU math already lives in your actual second language: WGSL. A WASM
  module would add a marshalling boundary to a path whose bottleneck isn't
  JavaScript.

  The deeper point: this codebase already delegates everything native-worthy to 
  native. Transcoding is ffmpeg (C, behind a binary boundary), USB hotplug is
  the usb native module, pixel work is WGSL on the GPU, media ingest is Chromium
  itself. The 26.7k LOC of TypeScript that remains is orchestration, policy,
  and UI — the exact layer where TS with strict contracts is the strongest tool
  available, and the layer a language swap would force you to rewrite rather
  than delete.

  So the language answer mirrors the Nest answer: the wins that look like
  "switch technology" are actually "finish the architecture you built" — the
  verified catalog items plus whatever the two spikes earn. If a second language
  ever enters this repo on merit, it'll be a small Rust sidecar for some
  specific device quirk the usb lib can't handle — a bounded tool, not a
  platform.

  Meanwhile both spikes are still running in their worktrees; I'll resume the
  catalog the moment their evidence lands.
